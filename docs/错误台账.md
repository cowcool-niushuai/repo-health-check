# 错误台账（出过什么错，怎么修的）

### 1. 密钥扫描返回明文片段
- **问题现象**：初始扫描器命中 `sk-` / `Bearer` 后直接返回原始行内容，存在二次泄露风险。
- **原因分析**：只做了正则匹配，未对敏感子串做展示脱敏。
- **修复方案**：新增 `mask_secret()` 与 `_mask_line_secrets()`，返回前将密钥中间部分替换为 `****`。
- **验证结果**：`tests/test_scanner.py` 断言明文子串不在返回结果中且包含 `****`。

### 2. 真实仓库实测出现大量误报（测试夹具 / Sphinx 脚本 / 代码注释）
- **问题现象**：实测 `pallets/flask` 得 59 分（C）、`psf/requests` 得 41 分（D），成熟开源项目被误判为高危阻塞。
- **原因分析**：`tests/certs/` 测试证书和 `tests/test_apps/.env` 被当成生产密钥泄露；`docs/make.bat` 同目录已有 `docs/Makefile` 仍被扣分；源码注释中的 `"C:\foo\bar.txt"` 和文档相对路径 `../../../../home/...` 被判为硬编码路径。
- **修复方案**：在 `app/scanner.py` 与 `app/scorer.py` 中区分测试夹具目录、同目录跨平台替代脚本、源码纯注释行以及相对路径前缀。
- **验证结果**：复测 `pallets/flask` 与 `psf/requests` 均得 100 分（A 级），`pytest` 6 项测试全通过。

### 3. 返回结果存在大量无效低危噪音、同文件重复项与 AI 建议误报
- **问题现象**：扫描 `tiangolo/fastapi` 返回 132 条风险（多语言文档中的示例路径 `/home/user/code/awesomeapp` 重复上百次），扫描 `psf/requests` 与本仓库自身也会输出大量测试文件/文档中的低危提示；且 `ai_advisor.py` 将低危测试密钥计入 `secret_count`，导致 100 分仓库仍被提示「存在高危密钥风险」。
- **原因分析**：`_scan_file_lines()` 对文档与测试代码仍发射低危 `RiskItem` 且未做单文件去重；`scan_repository()` 对已有跨平台替代的 `.bat` 和测试目录敏感文件仍逐条输出；`_rule_based_advice()` 未按 `severity` 过滤。
- **修复方案**：在 `app/scanner.py` 中跳过文档与测试文件的路径/内联密钥扫描、跳过已有跨平台替代的 Windows 脚本与测试夹具敏感文件，并按 `(category, matched_value)` 对单文件内命中去重；在 `app/ai_advisor.py` 中仅统计高危密钥与非低危路径/脚本风险。
- **验证结果**：`pallets/flask` 风险由 9 条降至 0 条，`psf/requests` 由 8 条降至 0 条，`tiangolo/fastapi` 由 132 条降至 2 条，`pytest -v` 10 项测试全通过。

### 4. 同一行包含多种密钥时，第二类密钥以明文回传
- **问题现象**：`A = "sk-proj-..."; B = "AKIA..."` 同一行时，`sk-` 被脱敏，但 `AKIA...` 原样出现在 `snippet` 中，违反「返回前必须脱敏」的硬要求。
- **原因分析**：`_mask_line_secrets(line, pattern)` 只接收首个命中的单一正则，脱敏后立即 `break`，不会处理该行其余密钥类型。
- **修复方案**：改为 `_mask_line_secrets(line)`，在截断前遍历全部 `_SECRET_PATTERNS` 完成脱敏。
- **验证结果**：新增 `test_all_secrets_on_one_line_are_masked`，断言 `sk-pro****3456` 与 `AKIAAB****MNOP` 同时出现且原始值不存在。

### 5. LLM Base URL 可被用户指定为内网地址，形成 SSRF
- **问题现象**：`/api/scan` 接受请求体中的 `llm_base_url`，服务端直接向其发起 POST，可访问 `127.0.0.1`、内网服务或云元数据地址，并把响应内容回显到 AI 建议中。
- **原因分析**：`generate_advice()` 只做了字符串拼接，没有任何协议/主机/IP 校验；`follow_redirects` 也未显式关闭。
- **修复方案**：新增 `_validate_llm_base_url()`，仅允许 `http/https`，阻断 localhost、内网/回环/链路本地/保留/组播 IP 及已解析到这些地址的域名；请求改为 `follow_redirects=False`；`ScanRequest` 为 URL/Key/模型字段增加长度上限。
- **验证结果**：新增 `test_llm_base_url_rejects_internal_targets`，内网地址直接降级规则引擎且不发起 HTTP 请求。

### 6. 仓库内符号链接可读取宿主文件；非 UTF-8 文件名导致 500
- **问题现象**：恶意仓库提交 `secret.py -> /etc/...` 或指向宿主密钥文件的符号链接时，扫描器会跟随链接读取仓库外内容；文件名含非 UTF-8 字节时，`/api/scan` 序列化响应失败返回 500。
- **原因分析**：`_scan_file_lines()` 仅用 `stat()` 与 `read_text()`，未校验真实路径是否位于克隆目录内；`rel_path`/顶层目录名直接使用 `os.walk` 解码出的 surrogate 字符串。
- **修复方案**：新增 `_is_within_root()`，README、`package.json` 与正文扫描在读取前先 `resolve()` 并确认仍位于仓库内，越界（含符号链接逃逸）直接跳过；新增 `_safe_text()` 将文件名中的非法字节替换为 `?` 后再返回。
- **验证结果**：新增符号链接逃逸与非 UTF-8 文件名回归测试；外部密钥不再被扫描，响应可正常 JSON 序列化。

### 7. 双重转义的反斜杠 Windows 路径漏报
- **问题现象**：`"C:\\\\Users\\\\bob\\\\x"`（Python/JSON/JS 字符串中的常见写法）检测不到，仅 `C:\Users` 与 `C:/Users` 能命中。
- **原因分析**：`_WIN_DRIVE_RE` 只允许单个 `\` 作为分隔符，遇到 `\\` 时路径匹配在第二个反斜杠处中断。
- **修复方案**：正则分隔符改为 `[/\\]{1,2}`；同时将 `tests/` 等夹具目录下的 `.bat/.cmd/.ps1/.vbs` 也按噪音跳过。
- **验证结果**：新增双重转义路径与测试目录 `.bat` 回归测试，现有 16 项测试全通过。
